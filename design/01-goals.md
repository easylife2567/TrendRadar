# 01 · 产品定位与目标

> 上游文档：[README.md](README.md)

## 1. 定位转变

| | 现状（推送工具） | 目标（AI 舆情监测中心） |
|---|---|---|
| 产品形态 | 定时任务跑完 → 推到 IM/邮件，看完即弃 | 常驻 Web 平台，随时打开、随时回溯 |
| 数据生命周期 | 报告当天有效，历史沉睡在 SQLite | 历史是核心资产，支撑趋势/对比/预测 |
| 交互方式 | 只读推送，无交互 | 搜索、筛选、下钻、追问（AI 分析） |
| 价值主张 | 别刷屏，只看关心的 | 看懂舆情：热度怎么起来、情绪往哪偏、接下来会火什么 |

**一句话定位**：面向个人和小团队的、可自托管的 AI 舆情监测中心--
数据自己攒、AI 自己配、部署在自己的机器上。

### 双轨产品线（2026-08-26 追加）

| | Track A · 监测中心 | Track B · 实验室工作台 |
|---|---|---|
| 回答的问题 | 舆情在怎么变化 | 今天的例行交付怎么最快做完 |
| 形态 | 看板 + 分析 | 人机协作任务引擎（筛选 -> AI -> 文件生成） |
| 设计文档 | 本档 + 02~07 | [08-workbench-design.md](08-workbench-design.md) |
| 状态 | 已排期（Phase 0–4） | 已声明，未排期（Phase 5–6） |
| 发行形态 | WSL 工作站 / Docker | 追加桌面 Release（[09](09-release-packaging.md)） |

两轨共用：新闻资源池、AI 基础设施、通知渠道、Web 产品壳。

## 2. 目标用户

1. **主要**：项目作者自己（自用驱动，保证产品真实性）
2. **次要**：开源项目的 self-host 用户--关注特定领域（公司名、竞品、技术关键词）的
   开发者/独立研究者/小团队公关
3. **实验室（Track B 追加）**：作者所在实验室的成员--既是监测中心的
   使用者，也是工作台（国际日报等例行任务）的用户；桌面发行版面向他们
4. **不做**：多租户 SaaS、企业级合规审计--那是另一个量级的产品
   （注意：**单个实验室内的多人使用**是目标范围，属 Track B v2 话题，
   与"多租户 SaaS"不是一回事）

## 3. 核心用户故事

### P0（没有就不叫监测中心）

- **US-1 日常总览**：打开首页，30 秒内看清今天各平台热点概况、
  我的关注词命中情况、有没有突然爆火的话题。
- **US-2 回溯**："上周三那个热点当时排多少？" 按日期翻任何一天的热榜。
- **US-3 检索**：全历史标题关键词搜索，看到命中列表及各平台分布。
- **US-4 话题追踪**：输入"特斯拉"，看到它在近 N 天的热度曲线、
  排名变化、生命周期阶段、跨平台分布、相关新闻列表。

### P1（让"AI"名副其实）

- **US-5 情感分析**：对某话题/某时段的新闻跑 AI 情感倾向分析，
  得到正/负/中比例与代表性标题，结果缓存并可回看。
- **US-6 爆火预警**：自动检测排名蹿升异常快的话题，在仪表盘置顶提示。
- **US-7 时期对比**：本周 vs 上周、本月 vs 上月的话题迁移与平台活跃度变化。
- **US-8 趋势预测**：基于历史排名序列给出"接下来可能升温"的话题候选。

### P2（产品化）

- **US-9 健康自察**：一眼看到各采集源的成功/失败状态、服务与调度是否正常。
- **US-10 手动刷新**：等不及下个调度周期时，点一下立即抓取/跑完整管线。
- **US-11 订阅管理**：在 Web 上管理推送给谁、推送什么（长期）。
- **US-12 双语**：界面中英文切换（延续 `docs/assets/i18n.js` 已有模式）。

### Track B · 工作台（已声明，详见 [08](08-workbench-design.md)）

- **US-B1 国际日报**：每天从国际新闻候选池中**人工选出**最重要的 6 条，
  AI 生成摘要、人工把关后，一键产出 Word + PDF 简报，
  并自动汇入 Excel 新闻历史资源池。人的时间只花在"选"和"把关"。
- **US-B2 任务复制**：同类例行任务（周报、竞品动态、话题简报）能以
  配置模板的方式快速复制出来，不需要写代码。
- **US-B3 下载即用**：实验室同学从 GitHub Releases 下载桌面版，
  双击、向导、当天可用（详见 [09](09-release-packaging.md)）。

## 4. 非目标（明确不做）

1. **不做写操作面（工作站/服务模式）**：v1 不提供网页改 `config.yaml`
   的功能（配置编辑已有 `docs/` 可视化编辑器，且改配置接口暴露公网风险高，
   见 [06-security.md](06-security.md)）。远程管理走 SSH / Cloudflare Access。
   **边界修正（Track B）**：桌面本机模式（仅 127.0.0.1、用户即机主）
   下的**首次运行向导**允许写配置，向导完成即自锁--这是 09 §4 的设计，
   与"公网不开写面"不矛盾。
2. **不做实时流**：数据粒度由调度周期决定（15~30 分钟），
   不追求秒级实时，不做 WebSocket 推送（v2 可考虑 SSE）。
3. **不改核心管线**：采集 → AI 分析 → 推送的现有逻辑一行不动，
   Web 层只读消费其产出。调度从 GitHub Actions 迁到 systemd timer，
   运行的仍是同一个 `python -m trendradar`。
4. **不引入重型基础设施**：不装 PostgreSQL/Redis/消息队列。
   SQLite 按日分库 + 进程内 TTL 缓存（`CacheService` 已有）够用，
   这是"轻量易部署"项目立场的延续。
5. **不放弃现有部署方式**：GitHub Actions / Docker / Cloudflare Pages
   静态报告全部保留且继续可用。WSL + Web 是**新增**形态，不是替换。

## 5. 成功度量（自用视角）

- 连续两周，日常看热点的主要入口从 IM 推送切到 Web 仪表盘
- 每周至少一次使用"话题追踪"或"时期对比"回答一个真实疑问
- 服务连续运行 30 天无人工干预（systemd 自愈算无人工）

## 6. 路线图（与 [07-implementation-plan.md](07-implementation-plan.md) 对应）

```
Phase 0  地基        WSL systemd + uv 环境 + Cloudflare Tunnel + 占位页
Phase 1  只读 API    web_server 包 + 核心查询端点 + API key 认证
Phase 2  MVP 前端    仪表盘 / 热榜 / 搜索 / 历史浏览（US-1~3）
Phase 3  监测能力    话题追踪 / 情感 / 对比 / 爆火 / 预测（US-4~8）
Phase 4  产品化      健康面板 / 手动刷新 / 认证完善 / i18n / 备份（US-9~12）
──────────────────────── Track B（已声明未排期）────────────────────────
Phase 5  工作台 MVP  国际日报全流程 + 文档生成栈 + 资源池（US-B1/B2）
Phase 6  发行版      桌面打包 + 首启向导 + release CI（US-B3）
```

依赖关系：Phase 0 与 Phase 1 可并行；Phase 2 依赖 Phase 1 的端点；
Phase 3 中情感分析依赖 Phase 1 引入的 AI 执行通道；Phase 4 随时插空。

## 7. 风险与开放问题

| 风险 | 影响 | 对策 |
|---|---|---|
| 家宽上行带宽小 | 页面慢 | 前端产物gzip后 <500KB；图表数据分页；CF 边缘缓存静态资源 |
| WSL/Windows 重启 | 服务中断 | systemd `Restart=always` + Windows 任务计划自启；接受工作室级可用性（见 05 §7） |
| AI 情感分析调用被滥用（公网） | token 账单 | 端点默认认证 + 进程级并发闸 + 结果缓存 + 每日调用上限 |
| newsnow 上游限流 | 抓取失败 | 现有管线已有重试/退避；`crawl_source_status` 在健康面板透出 |
| 历史数据规模增长 | 查询变慢 | 按日分库天然分片；跨日查询在 tools 层已按日期迭代；必要时加汇总缓存 |
